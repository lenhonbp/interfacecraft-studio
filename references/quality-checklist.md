# InterfaceCraft Quality Checklist

Use this checklist as a final review. Mark each item as pass, revise, or not applicable, and attach evidence or a concrete follow-up for every revision.

| Area | Review question | Status / evidence |
|---|---|---|
| Goal | Does each major screen support a defined user, player, or product goal? | |
| Hierarchy | Can users identify the primary information and action quickly? | |
| Flow | Are entry, success, interruption, cancellation, and recovery paths defined? | |
| States | Are loading, empty, error, disabled, confirmation, and edge states specified? | |
| Terminology | Are labels, commands, and messages consistent and unambiguous? | |
| Interaction | Are affordance, feedback, focus, validation, and undo/cancel behavior clear? | |
| Game readability | Is critical information legible at gameplay distance and during high-intensity moments? | |
| Responsive behavior | Are layout, priority, overflow, safe-area, and orientation rules defined? | |
| Accessibility | Are contrast, text scale, focus, target size, motion, semantics, and alternate input considered? | |
| Content | Does copy explain the action, consequence, status, and next step without unnecessary words? | |
| Visual system | Are tokens, components, variants, spacing, type, and color roles consistent? | |
| Feasibility | Are asset, performance, localization, and implementation constraints acknowledged? | |
| Handoff | Could another designer or developer implement the design without guessing? | |
| Validation | Are acceptance criteria and the next validation method explicit? | |

## Severity model

Classify issues as **blocker** when they prevent task completion or create a serious accessibility or safety problem; **high** when they cause frequent confusion or materially harm the core journey; **medium** when they reduce efficiency or consistency; and **low** when they are primarily polish or preference.

## Review summary

Conclude with the three highest-impact findings, the recommended order of fixes, unresolved decisions, and the smallest useful validation activity.
